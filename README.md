# Z80 SBC Monitor — extended Grant Searle Monitor

This project is based on Grant Searle's Z80 Monitor for the Simple Z80 / CP/M SBC.

The original Monitor was adapted for building with **SjASMPlus** and extended with several debugging and development features.

The main goals of this project are:

- preserve the original Monitor behaviour;
- make it compatible with Intel HEX files generated by modern toolchains;
- add a built-in memory viewer;
- make Monitor development possible without repeatedly removing and reprogramming the EPROM.

> The original Grant Searle source is for non-commercial use and requires acknowledgement.  
> The original copyright notice is preserved in the source code.

## Changes

### 1. SjASMPlus build support

The original Monitor source was adapted for use with `sjasmplus`.

The Monitor is still assembled for its original address space:

```text
0000h-3FFFh
```

RAM workspace used by the Monitor starts at:

```text
4000h
```

The ROM image is built as a 16 KiB binary image.

Typical build tools:

- `sjasmplus`
- `srecord`
- `ascii-xfr`

---

## Intel HEX loader fix

The original Monitor loader only distinguished between:

```text
type 01 = End Of File
```

and everything else.

Effectively the original logic was:

```text
if record type == 01:
    EOF
else:
    treat as data
```

This is incorrect for modern Intel HEX files, because Intel HEX defines several record types.

For example, SjASMPlus may generate:

```text
:020000040000FA
```

This record means:

```text
02      record length = 2
0000    address field
04      Extended Linear Address record
0000    record data
FA      checksum
```

Record type `04` is **not memory data**.

However, the original Monitor interpreted it as a normal data record and executed the equivalent of:

```text
0000h <- 00h
0001h <- 00h
```

This corrupted the Monitor reset vector.

The correct reset vector begins with:

```text
F3 C3 ...
```

but after loading such an Intel HEX file it became:

```text
00 00 ...
```

The Monitor itself continued running because it was already executing code elsewhere, but:

```text
JP 0000h
```

and warm reset no longer worked.

### Fixed behaviour

The loader now explicitly handles Intel HEX record types:

```text
Type 00   Data record
          Data is written to RAM

Type 01   End Of File
          Loading is completed

Other     Record is consumed and checksum-checked,
          but its payload is NOT written to RAM
```

This includes records such as:

```text
02 - Extended Segment Address
03 - Start Segment Address
04 - Extended Linear Address
05 - Start Linear Address
```

Unsupported records are therefore safely ignored while keeping the input stream and checksum calculation synchronized.

The actual memory write is now performed only for a `type 00` record.

## Memory viewer

A new Monitor command has been added:

```text
Mxxxx
```

where `xxxx` is the start address.

Example:

```text
>M8000
```

The viewer displays a 256-byte memory page as 16 lines of 16 bytes.

Example layout:

```text
8000: 3E 41 D7 C9 ...    >A......
8010: ...
...
```

Each line contains:

- memory address;
- hexadecimal byte values;
- printable ASCII representation.

The memory viewer supports navigation:

```text
N / SPACE       next 256-byte page
P               previous 256-byte page
G               go to another address
Q               quit to Monitor

Cursor Up       previous page
Cursor Down     next page
PgUp            previous page
PgDn            next page
```

The viewer uses the existing Monitor console routines via the standard RST entry points.

The command is integrated into the main Monitor command loop as:

```text
Mxxxx       - Memory dump/viewer
```

## Why RAM-based Monitor testing is needed

Normally the Monitor occupies:

```text
0000h-3FFFh
```

in EPROM.

Testing a modified Monitor by programming the EPROM after every source change is inconvenient and also causes unnecessary EPROM socket and device wear.

It is also not possible to simply upload a new Monitor to address `0000h` using the running Monitor, because the upload would overwrite the code that is currently executing.

To solve this, a RAM-based test procedure is used.

---

# Testing a new Monitor in RAM

The test procedure keeps the original EPROM Monitor available as a recovery environment.

The new Monitor is assembled normally for:

```text
0000h-3FFFh
```

It is important that the Monitor source continues to use:

```asm
ORG $0000
```

The Monitor must **not** be relocated during assembly because it contains absolute addresses, RST vectors and the IM2 interrupt vector.

Instead, the already assembled binary image is temporarily loaded into RAM at another address.

The current test memory layout is:

```text
0000h-3FFFh   ROM Monitor / later RAM Monitor

4000h-40xxh   Monitor workspace and stack

4100h         RAM loader

5000h-8FFFh   temporary copy of new Monitor image
```

---

## Step 1 — Build the Monitor

The new Monitor is assembled normally:

```text
ORG 0000h
```

producing:

```text
build/monitor-sjasmplus.bin
```

This is a normal 16 KiB Monitor image intended for:

```text
0000h-3FFFh
```

---

## Step 2 — Create a temporary HEX image at 5000h

The binary image is converted to Intel HEX with an offset:

```bash
srec_cat build/monitor-sjasmplus.bin -Binary \
    -offset 0x5000 \
    -o build/monitor-test.hex -Intel \
    -line-length 80
```

Note that this does **not** relocate the code.

The code is still assembled for `0000h`.

Only the addresses used while transferring the image to RAM are changed.

The resulting Monitor image is uploaded to:

```text
5000h-8FFFh
```

---

## Step 3 — Load the RAM loader

A small loader is assembled at:

```asm
ORG $4100
```

The loader performs:

```text
DI

disable ROM

copy:
    5000h-8FFFh
        ->
    0000h-3FFFh

JP 0000h
```

The current loader core is:

```asm
        ORG $4100

start:
        DI

        OUT ($38),A

        LD HL,$5000
        LD DE,$0000
        LD BC,$4000
        LDIR

        JP $0000
```

The actual test loader also writes the text:

```text
RAM
```

to unused bytes in page zero before starting the Monitor.

This provides a simple indication that the RAM image was installed successfully and can be inspected after a failed test or reset.

### Why the loader is at 4100h

The temporary Monitor image occupies:

```text
5000h-8FFFh
```

Therefore the loader must not be placed inside this range.

For example, placing the loader at `8000h` would overlap the temporary Monitor image and one upload would overwrite part of the other.

`4100h` is outside both the Monitor image and its normal ROM address range, making it suitable for the loader.

---

## Step 4 — Upload and start

The current test sequence is:

```bash
ascii-xfr -s -l 50 build/monitor-test.hex > /dev/ttyUSB0

ascii-xfr -s -l 50 build/rom_loader.hex > /dev/ttyUSB0

printf 'g4100\r' > /dev/ttyUSB0
```

The original ROM Monitor receives both HEX files.

After:

```text
G4100
```

the RAM loader:

1. disables interrupts;
2. disables the EPROM;
3. copies the new Monitor from `5000h` to `0000h`;
4. jumps to `0000h`.

The new Monitor then starts exactly as it would from ROM.

---

# Recovery after a failed test

If the new Monitor crashes or hangs, no EPROM reprogramming is required.

Perform a **hard reset**.

The hardware reset restores the ROM mapping and the original EPROM Monitor becomes available again.

The next test build can then be uploaded.

The normal development cycle therefore becomes:

```text
edit source
    ↓
assemble
    ↓
upload new Monitor to 5000h
    ↓
upload loader to 4100h
    ↓
G4100
    ↓
test Monitor from RAM
    ↓
hard reset if necessary
    ↓
repeat
```

The EPROM only needs to be programmed after the new Monitor version has been tested successfully.

# Automated test script

The complete procedure can be automated with a shell script.

Example:

```bash
#!/bin/bash
set -e

PORT=/dev/ttyUSB0

mkdir -p build

echo "Building Monitor..."

sjasmplus \
    --raw=build/monitor-sjasmplus.bin \
    --lst=build/monitor-sjasmplus.lst \
    --sym=build/monitor-sjasmplus.sym \
    --cleanonerror \
    monitor-sjasmplus.asm

echo "Creating RAM test image..."

srec_cat build/monitor-sjasmplus.bin -Binary \
    -offset 0x5000 \
    -o build/monitor-test.hex -Intel \
    -line-length 80

echo "Building RAM loader..."

sjasmplus \
    --raw=build/rom_loader.bin \
    --lst=build/rom_loader.lst \
    --sym=build/rom_loader.sym \
    --cleanonerror \
    rom_loader.asm

echo "Creating RAM loader HEX..."

srec_cat build/rom_loader.bin -Binary \
    -offset 0x4100 \
    -o build/rom_loader.hex -Intel \
    -line-length 80

echo "Uploading Monitor..."

ascii-xfr -s -l 50 \
    build/monitor-test.hex > "$PORT"

echo "Uploading RAM loader..."

ascii-xfr -s -l 50 \
    build/rom_loader.hex > "$PORT"

echo "Starting RAM Monitor..."

printf 'g4100\r' > "$PORT"

echo "Done."
```

---

# Serial upload speed

The Grant Monitor uses small serial receive buffers, so sending an Intel HEX file without pacing may overflow the input buffer.

`ascii-xfr` is therefore used with a line delay:

```bash
ascii-xfr -s -l 50 file.hex > /dev/ttyUSB0
```

If loading becomes unreliable, increase the delay.

# Development workflow

Recommended workflow:

```bash
# Edit Monitor source

./test-monitor.sh
```

Then test:

```text
?
M0000
M4000
```

For testing the Intel HEX loader, load a HEX file containing an Extended Linear Address record such as:

```text
:020000040000FA
```

Before the loader fix, this record corrupted:

```text
0000h = F3
0001h = C3
```

into:

```text
0000h = 00
0001h = 00
```

With the fixed loader, the record is consumed but does not write to RAM.

The memory viewer can be used immediately afterwards:

```text
M0000
```

and the reset vector should remain intact:

```text
0000: F3 C3 ...
```

This also serves as a regression test for the Intel HEX loader fix.

# Current Monitor additions

Compared with the original Monitor, this version currently includes:

- SjASMPlus-compatible source;
- proper 16 KiB ROM binary generation;
- corrected Intel HEX record handling;
- support for modern Intel HEX files containing non-data records;
- built-in `Mxxxx` memory viewer;
- hexadecimal and ASCII memory display;
- memory page navigation;
- ANSI cursor/PgUp/PgDn handling;
- RAM-based Monitor development and testing;
- small RAM bootstrap loader;
- automated build/upload/test workflow.
